# rear-theme — Vic Pimentel portfolio

WordPress block theme built on ACF Blocks. All PHP is loaded from `core/` and `app/` recursively by `functions.php`. No framework — just WordPress + ACF + a thin layer of custom helpers.

## Block registration

`core/blocks.php` hooks `scan_and_register_blocks()` to `init`. It:

1. Recursively walks `src/content/blocks/` via `scan_block_dirs()`: any directory containing a `{dirname}.php` matching its own name is a block, at any nesting depth (e.g. `library/text-1`, or `library/accordion/accordion-1` when a category has subcategory folders); anything else is walked further as a category/subcategory folder. A directory without a matching `{block-name}.php` is never treated as a block. The block's top-level category (`library`, `custom`, `inner-blocks`, `wrappers`) is always the first path segment relative to the blocks root, regardless of how deep the block itself sits
2. Loads `config.php` if present — this file sets a `$config` array. The framework-only keys `field_defaults`, `field_choices`, `repeater_content`, and `bail_message` are collected into their registries here and stripped — they never reach `block.json` (see the block-builder skill §3)
3. Builds `block.json` arguments from `$config`, with these defaults:
   - `category`: `custom-blocks`
   - `icon`: `admin-comments`
   - `supports.jsx`: `true`, `supports.anchor`: `true`, `supports.align`: `false`
   - `acf.mode`: `preview`, `acf.renderTemplate`: `{block-name}.php`
   - `attributes.preview_image`: URL to `preview.png` in the block folder
4. Auto-registers block CSS from `public/blocks/{name}.css` and JS from `public/blocks/{name}.js` if they exist, and injects the handles into the JSON
5. Calls `generate_block_json()` — writes `block.json` to disk **only when `WP_DEBUG` is true**; do not edit `block.json` by hand
6. Calls `register_block_type($block_dir)` which reads the written `block.json`

**`library/` blocks are gated by the `LOAD_LIBRARY_BLOCKS` constant**, defined in `app/config.php` (loaded before `core/` by `functions.php`; `core/blocks.php` holds a client-safe `false` fallback). When `true`, `library/` blocks register normally so they can be tested in the editor. When `false`, `scan_and_register_blocks()` skips them entirely — no `block.json`, no CSS/JS registration, no `register_block_type()` call — so they never appear in the block inserter, while the source stays in the repo as reference. It's a hardcoded PHP constant, not an ACF options field, specifically so a client can never toggle it from wp-admin. Keep it `true` while developing the shared library; set it to `false` when handing a project to a client.

**Minimum block structure:**
```
src/content/blocks/library/my-block/
├── config.php          # required: sets $config['title'], optionally icon/category/keywords
├── my-block.php        # required: render template
├── my-block.scss       # optional: compiled to public/blocks/my-block.css
├── my-block.js         # optional: compiled to public/blocks/my-block.js
├── preview.png         # required for editor preview image
└── acf-json/           # ACF field group JSON for this block
```

**`config.php` shape:**
```php
$config = [
    'title'    => 'My Block',
    'icon'     => 'align-center',         // Dashicon slug
    'category' => 'custom-blocks',        // optional — defaults to custom-blocks; set only for inner-blocks | wrappers | library
    'keywords' => 'my-block',             // optional — defaults to the block name
    'field_defaults' => [                 // optional — per-block default_value overrides (core/acf.php)
        'title.html_tag' => 'h1',         //   clone sub-fields, global fields (bg_color, spacing_*),
        'bg_color' => 'background-6',     //   nested paths (button.style); editors can still change them —
    ],                                    //   see the block-builder skill §3 for syntax and layers
    'field_choices' => [                  // optional — per-block visible-choice restriction (core/acf.php)
        'bg_color' => ['background-1', 'background-7'], //   plain list: restrict only, keep original labels;
        // 'bg_color' => ['background-1' => 'Cor Principal'], //  assoc key=>label map: restrict AND relabel too
    ],                                    //   same name/dot-path syntax as field_defaults; editor-only,
                                           //   doesn't touch already-saved values — see skill §3
    'bail_message' => 'Publique materiais para exibir este bloco.', // optional — editor-preview notice when the block bails/renders nothing; generic English default otherwise
    'repeater_content' => [               // optional — initial repeater rows (with per-row content/styles) every fresh
        'items' => [['title' => '…']],    //   instance starts with, in form/preview/frontend — see skill §3, accordion-2
    ],
];
```

## Block render template

Every block render template follows this pattern:

```php
<?php
/** @var $block */
$fields = get_fields();

ob_start();
?>
    <div class="wrapper">
        <?php component('headline', $fields['title']) ?>
        <?php component('buttons', ['buttons' => $fields['buttons']['buttons']]) ?>
    </div>
<?php
render(ob_get_clean(), $block);
```

`get_fields()` returns `false` (not an empty array) when no ACF fields are configured for the block — use `get_fields() ?: []` to guarantee an array, or guard with `isset()`/`empty()` before every field access.

`render($content, $block, $attr = [])` (defined in `core/blocks.php`) wraps the content in:
```html
<section
  class="block block-{name} bg-{color} spacing-top-{x} spacing-bottom-{y} {customClassName}"
  data-block="{name}"
  data-block-id="{id}"
  id="{anchor}">
  {content}
</section>
```

It reads the global ACF fields `bg_color`, `spacing_top`, and `spacing_bottom` automatically. Custom spacing values are emitted as CSS variables (`--spacing-top-mobile`, etc.) on the `style` attribute.

## Component pattern

Components live in `src/content/components/{tier}/{name}/{name}.php`, where `{tier}` is one of three subfolders:

| Tier | Purpose |
|---|---|
| `style-guide/` | Base design-system components — the generic building blocks (accordion, button, buttons, form, headline, icon, image, image-video, link, modal, pagination, rich-text, social-media, swiper-controls, tabs, video-player) |
| `custom/` | Project-specific components (header, footer, mega-menu, card-material, card-project, etc.) |
| `library/` | Reference-only components not chosen for this project — source stays in the repo but their compiled CSS/JS is excluded from the enqueue (see `library_component_names()` in `core/core.php` and its use in `core/assets.php`). Mirrors `blocks/library/`'s role, but components don't have a `LOAD_LIBRARY_BLOCKS`-style kill switch — exclusion is automatic based on folder location. |

Call them with the bare name — you never need to know or pass the tier:
```php
// Single-arg form
component('headline', $args);
component('button', ['data' => $field, 'class' => 'extra-class']);

// Two-arg form — $args2 wins on key collision.
// Use when the primary data is an ACF sub-array and the caller needs to impose display settings on top.
component('image-video', $fields['image_video'], ['max_size' => 'large']);
```

`component()` is defined in `core/core.php`. It normalises args (ensures `name` and `class` keys exist, injects caller path info) and delegates to `get_template_part()`. `resolve_component_folder()` (`core/core.php`) resolves the bare name to its tier folder by checking `style-guide/`, then `custom/`, then `library/` for a matching directory, caching the result. `component()` also injects `block_parent`, `block_folder`, and `file_name` from the call site — these power `parts_path()` resolution and must not be overwritten by callers. `block_folder` carries the full path relative to the components/blocks root (e.g. `style-guide/tabs`), so `parts_path()` stays correct regardless of nesting.

**Where to put a new component:** design-system-level building block → `style-guide/`; bespoke to this project → `custom/`; built as a reference but not used on this project → `library/`.

Every component file:
1. Receives `$args` (already includes `name` and `class`)
2. Merges defaults with `wp_parse_args($args, $default_args)`
3. Builds inner HTML in `ob_start()` / `ob_get_clean()`
4. Calls `render_component(ob_get_clean(), $args)` (defined in `core/components.php`)

`render_component()` emits:
```html
<{html_tag} class="component component-{name} {extra-class}" data-component="{name}">
  {content}
</{html_tag}>
```

`html_tag` defaults to `div`; components override it when semantically appropriate (e.g. `button.php` sets it to `a` or `button`).

**Additional helpers** (defined in `core/core.php`):
- `section('name', $args)` — loads `src/content/sections/{name}/{name}.php`
- `part('name', $args)` — loads `src/content/parts/{name}.php`
- `options('field_name')` — shorthand for `get_field('field_name', 'options')`

## Block and component JavaScript

Block JS files (`src/content/blocks/{category}/{name}/{name}.js`) and component JS files (`src/content/components/{tier}/{name}/{name}.js`) use a common entrypoint pattern:

```js
// Block
window.theme.block('block-name', el => {
    // el is the <section data-block="block-name"> DOM element
    // called once per block instance on DOMContentLoaded
});

// Component
window.theme.component('component-name', el => {
    // el is the outer component wrapper (data-component="component-name")
    // called once per component instance on DOMContentLoaded
});
```

`window.theme` is defined in `src/scripts/core.js` (imported by `app.js`). Both methods scan the DOM for matching `data-block` / `data-component` attributes and invoke the callback for each found element. Third-party packages registered via `window.theme.registerPackages()` (e.g. Swiper, in `src/scripts/global/swiper.js`; Lenis, in `src/scripts/global/lenis.js`) are available in any block/component JS as `window.theme.packages.*`.

**`window.theme` is `Object.freeze()`'d — never assign a new property directly onto it.** `core.js` returns `Object.freeze({component, block, section, init, setup, packages, registerPackages})`; in non-strict script code (this bundle isn't `type="module"`), assigning a new top-level property (`window.theme.myThing = ...`) doesn't throw — it silently no-ops, so the property is simply never there, with zero console error to explain why. `window.theme.packages` is the one property whose *contents* stay mutable (only the outer container is frozen), so any new shared loader/utility a global script wants to expose must go through `registerPackages({ myThing })` and be read back as `window.theme.packages.myThing`, exactly like Swiper/Lenis/lightGallery — never a direct assignment, even for something that isn't really a "third-party package" (confirmed the hard way: `src/scripts/global/google-maps.js`'s shared Maps loader silently failed site-wide, with `window.theme.loadGoogleMaps is not a function` at every call site, until switched to `registerPackages({ loadGoogleMaps })` / `window.theme.packages.loadGoogleMaps()`).

**Smooth scroll (Lenis)** — `src/scripts/global/lenis.js` runs Lenis in its default window-scroll mode (no custom wrapper/content element), which smooths mouse-wheel/touch scroll input by lerping the *real* `scrollTop` each frame rather than transforming a wrapper — this is what keeps it compatible with `position: sticky` (the transform-wrapper approach used by older libraries like Locomotive Scroll breaks sticky; this mode doesn't). It's disabled automatically when `prefers-reduced-motion: reduce` is set, and `window.theme.packages.lenis` is `null` in that case. Any code that needs to scroll the page programmatically should call `lenis.scrollTo(target, {offset})` when `window.theme.packages.lenis` is truthy, and fall back to native `window.scrollTo({behavior: 'smooth'})` otherwise — see `src/scripts/global/scroll-to.js` for the reference pattern. To disable Lenis for a client (e.g. on request), just remove the `import './global/lenis'` line from `app.js` — `scroll-to.js`'s fallback already handles Lenis being absent, no other change needed.

**Any element with its own independent `overflow: auto/scroll` (a modal, a dropdown panel, a sidebar drawer) needs `data-lenis-prevent` on it.** Because Lenis listens globally in window-scroll mode, it intercepts wheel/touch input over a nested scrollable element too — without this attribute, scrolling inside that element instead (or also) smooth-scrolls the page behind it. Lenis checks for this attribute natively (no JS wiring needed on this project's side, see `node_modules/lenis`'s `prevent` handling) — just add `data-lenis-prevent` to the scrollable element's own markup. The `modal` component (`src/content/components/style-guide/modal/modal.php`) already does this; copy the same attribute onto any new custom-scrolling element.

**Global scripts must guard against admin.** `public/app.js` (the whole frontend bundle, including everything in `src/scripts/global/`) is also enqueued in wp-admin (`core/assets.php`, `theme_enqueue_admin_assets()`) so ACF's block-preview iframe renders blocks with real frontend behavior. Any script in `src/scripts/global/` that isn't scoped to a specific block/component instance (page-wide scroll/resize/keyboard handling, third-party init, etc.) must bail unless `isFrontend()` (`src/scripts/global/is-frontend.js`) is true — same guard `lenis.js`, `scroll-to.js`, `member-modal.js` and `post-views.js` use. It checks the `is-frontend` body class (`core/core.php` `body_class` filter), which is absent both in wp-admin and inside the block editor's canvas iframe; the older `window.initializer.isAdmin` check misses the iframe (no `initializer` there), which is how Ember blanked every ACF preview. `ember.config.js` and `common/_critical-overlays.scss` key off the same class. Block/component JS *does* run in the editor: `core.js` initializes blocks there via a `MutationObserver`, and `theme_enqueue_editor_iframe_styles()` (`core/assets.php`) pushes app/component/section/static CSS (styles only) into the iframe.

**No jQuery.** Removed from the frontend entirely — every plugin currently in use (including Contact Form 7) works without it. Write new block/component JS in vanilla JS; for any AJAX need, use `fetch()` (covers everything `$.ajax()` did for this stack — JSON, `FormData`/file uploads, headers, credentials, cancellation via `AbortController` — the one gap is native upload-progress events, which would need `XMLHttpRequest` for that one narrow case, still no jQuery required). Don't reintroduce a jQuery dependency for a new feature without a real, specific reason.

## AJAX endpoints

Two places to put a `wp_ajax_*` handler, depending on scope — both are auto-loaded, nothing else needs to be touched or registered anywhere:

| Scope | Location | How it's loaded |
|---|---|---|
| Site-wide (not tied to one block) | `app/ajax/{name}.php` | `app/` is already recursively `require_files()`'d by `functions.php` — no extra wiring |
| Block-specific | `{block-dir}/{block-name}-ajax.php`, co-located with the block's own `.php`/`.scss`/`.js` | `scan_and_register_blocks()` (`core/blocks.php`) `require_once`s it by exact filename match, right next to where it reads the block's `config.php` |

Each file is self-contained and registers its own hook(s) at the bottom, exactly like `app/post-types/*.php` self-registers on `init`:

```php
<?php

function ajax_my_action(): void
{
    check_ajax_referer('theme_ajax', 'nonce'); // always verify the nonce first

    // ...sanitize $_POST, do the work...

    wp_send_json_success(['...' => '...']); // or wp_send_json_error([...], $status)
}
add_action('wp_ajax_my_action', 'ajax_my_action');
add_action('wp_ajax_nopriv_my_action', 'ajax_my_action'); // add only if guests must be able to call it
```

**Frontend JS calls it via `window.themeAjax`** (`core/assets.php`'s `theme_enqueue_frontend_assets()`, `wp_localize_script` on `theme-app-script`) — `.ajaxUrl` (`admin_url('admin-ajax.php')`) and `.nonce` (created against the shared `'theme_ajax'` action, matching every handler's `check_ajax_referer('theme_ajax', 'nonce')` call). This is the frontend counterpart to `admin-initializer`'s `initializerData.adminAjax`, which only enqueues in wp-admin:

```js
const body = new FormData();
body.append('action', 'my_action');
body.append('nonce', window.themeAjax.nonce);
// ...append other fields...

fetch(window.themeAjax.ajaxUrl, {method: 'POST', body})
    .then(r => r.json())
    .then(data => { /* ... */ });
```

`app/ajax/post-views.php` (real view-count tracking behind listing-2's "Mais lidas", site-wide since any single post can be viewed) and `src/content/blocks/library/listing/listing-3/listing-3-ajax.php` (listing-3's own search/filter/load-more, block-specific since nothing else calls it) are the two reference implementations — both `nopriv` since most readers are logged out, both validate their input (post exists and is published; search/category/paging values sanitized and bounds-checked) before doing anything. Sanitize every `$_POST` value read from an AJAX request the same as any other user input — a `nopriv` endpoint is reachable by anyone, and even a logged-in-only endpoint should still validate `current_user_can()` for whatever it's about to do, not just that *some* nonce-holding user is asking.

## ACF JSON conventions

**The ACF admin UI is gated by the `SHOW_ACF_ADMIN` constant**, defined in `app/config.php` (with a client-safe `false` fallback in `core/acf.php`) — same pattern and rationale as `LOAD_LIBRARY_BLOCKS`: a hardcoded PHP constant a client can never toggle from wp-admin. `true` while developing (field groups editable in the UI, saves flow to versioned JSON as documented below); set it to `false` on client handoff — all fields keep working, but the Field Groups screen disappears, removing the risk of a client breaking field groups or overwriting the versioned JSON from production.

### Save/load routing (`core/acf.php`)

ACF field group JSON is routed by the **title prefix** of the field group. Prefixes are case-sensitive and must match exactly:

| Title prefix (EN) | Title prefix (PT-BR) | Saved to |
|---|---|---|
| `Global Field: *` | `Campo Global: *` | `acf-json/global-fields/` |
| `Custom Field: *` | `Campo Customizado: *` | `acf-json/custom-fields/` |
| `Theme Settings: *` | `Config Site: *` | `acf-json/options-pages/` |
| `Menu: *` | — | `acf-json/menu/` |
| `Post Type: *` | — | `acf-json/post-types/` |
| `Template: *` | — | `acf-json/templates/` |
| `Block: {name}` | `Bloco: {name}` | `src/content/blocks/**/{name}/acf-json/` |
| `Inner Block: {name}` | — | `src/content/blocks/**/{name}/acf-json/` |
| `Wrappers: {name}` | — | `src/content/blocks/**/{name}/acf-json/` |

File names are derived from the title: spaces and underscores → hyphens, lowercased, `.json` appended. Example: `"Block: Text-1"` → `block-text-1.json`.

All save paths are also registered as load points. The `acf/settings/load_json` filter also recursively discovers every `acf-json/` subfolder inside the blocks directory.

### Three tiers of field groups

**1. Global fields** (`acf-json/global-fields/`) — location rule `block == all`. Automatically appended to every ACF block. Current global fields:
- `global-field-vertical-spacing.json` — `spacing_top`, `spacing_bottom` with optional custom px values per breakpoint
- `global-field-background-color.json` — `bg_color`
- `global-field-header.json` — header-specific options

**2. Custom fields** (`acf-json/custom-fields/`) — standalone reusable field groups that exist **only to be cloned**. Their location rule is an impossible condition (`post_type == post AND post_type != post`) so they never appear standalone. Current custom fields: `headline` (text + style + html_tag), `button`, `buttons`, `link`, `image-video`, `form`.

**3. Block-specific fields** (`src/content/blocks/{category}/{name}/acf-json/`) — one JSON file per block, co-located with the block files. Location rule: `block == acf/{block-name}`. These clone custom fields by group key using ACF's `clone` field type:
```json
{
  "type": "clone",
  "clone": ["group_667e1dc9e62a0"],
  "display": "group",
  "prefix_name": 1
}
```
With `prefix_name: 1` the cloned fields are namespaced (e.g. `title_text`, `title_style`). With `display: "seamless"` they are merged flat.

### Portuguese locale

`acf-json-br/` mirrors `acf-json/` with Portuguese field labels. Both directories are registered as load points. When adding a new global/custom field group, add it to both. In a project only one locale should be used by renaming the folder to `acf-json` and removing the other folder.

**Block-level ACF JSON is single-locale by design** — no `-br` mirror per block. Library blocks are authored with PT-BR display strings; adopting one in an English project means translating display strings only (labels, never field `name`s — slugs are always English in both locales), verified with the script in the block-builder skill. See that skill's "Library-block locale" section in §5.

## Asset build pipeline

All source assets live in `src/`. The build output goes to `public/` at the theme root. **Never edit files in `public/` directly.**

### Commands (run from `src/`)
```bash
npm start        # clean build + watch (default: --rebuild=true)
npm run build    # one-shot clean build via gulp build
```

### What gets compiled

`.theme.json` defines `contentPaths`, which the gulpfile uses to discover source files:

| Content type | SCSS source | JS source | Output |
|---|---|---|---|
| global | `src/styles/*.scss` | `src/scripts/app.js` | `public/*.css / public/app.js` |
| static | `src/styles/static/*.scss` | `src/scripts/static/*.js` | `public/static/` |
| admin | `src/styles/admin/*.scss` | — | `public/admin/` |
| blocks | `src/content/blocks/**/*.scss` | `src/content/blocks/**/*.js` | `public/blocks/{name}.css / .js` |
| components | `src/content/components/**/*.scss` | `src/content/components/**/*.js` | `public/components/{name}.css / .js` (library/ tier compiles but is excluded from the enqueue) |
| sections | `src/content/sections/**/*.scss` | `src/content/sections/**/*.js` | `public/sections/{name}.css / .js` |
| templates | `src/styles/templates/*.scss` | `src/scripts/templates/*.js` | `public/templates/` |

SCSS is compiled with `gulp-dart-sass` (compressed output) + `autoprefixer`. JS is bundled with webpack (production mode, source maps).

In watch mode, content files (blocks, components, sections) are compiled individually on change — only the changed file recompiles, not the full bundle.

### SCSS abstracts

Available to all SCSS files via `includePaths: ['styles']`:
- `abstract/_variables.scss` — design tokens
- `abstract/_mixins.scss` — reusable mixins
- `abstract/_breakpoints.scss` — breakpoint map (used with `include-media`)
- `abstract/_functions.scss` — SCSS functions (`rem`, `fluid`)
- `abstract/_contexts.scss` — context/state selectors

### Sizing functions (`abstract/_functions.scss`)

**`rem($values, $return-unit: true)`**

Converts px to rem by dividing by 16. Accepts a single value or a space-separated list:
```scss
font-size: rem(24);          // → 1.5rem
padding: rem(16 24 16 24);   // → 1rem 1.5rem 1rem 1.5rem
```
Pass `$return-unit: false` to get the bare number for use in further SCSS calculations.

**`fluid(...)` — piecewise-linear, any number of stops**

One CSS expression, no media queries. Each segment between two stops adds `clamp(0, (100vw − stopᵢ) · slopeᵢ, Δᵢ)` (lengths only — no typed division needed); flat segments emit nothing. Below the first stop the value pins to the first value, above the last stop to the last value.

```scss
font-size: fluid((150 104 54 54 32 24));            // 6 values in Figma mode order: 1920 · 1440 · 1280 · 1024 · 600 · 380
gap: fluid((mobile-small: 16, tablet: 24, 1920px: 48)); // any stops, breakpoint names or px
padding: fluid(16, 24);                             // legacy 2-value form: 380 → 1920
margin: fluid(16, 32, 'mobile-large', 'tablet');    // legacy form with a custom range
font-size: fluid((150 104 54 54 32 24), $extrapolate: true); // keeps scaling past 1920 (no-max-width hero/footer)
```

Design tokens are tables in `abstract/_variables.scss` (`$font-size-tokens`, `$space-tokens`, `$radius-tokens`), printed once as CSS custom properties on `:root` by `common/_tokens.scss` (`--fs-h-3xl`, `--space-l`, `--radius-m`…). The SCSS variables (`$fs-h-3xl`, `$space-l`, `$radius-m`, and the text-style maps `$heading-*`, `$p-*`, `$action-*`, `$link-*`, `$special-*`) just reference those properties, so the long `calc()` is emitted once, not per use.

Breakpoints (`abstract/_breakpoints.scss`) mirror Figma's 6 Dimensions modes:

| Name | px |
|---|---|
| `mobile-small` | 380 |
| `mobile-large` | 600 |
| `tablet` | 1024 |
| `desktop-small` | 1280 |
| `desktop-medium` | 1440 |
| `desktop-large` | 1920 |

**When to use each approach:**

| Need | Tool |
|---|---|
| Size that scales with viewport (font, padding, gap, spacing) | a token (`$space-*`, `$fs-*`) or `fluid((…6 values…))` |
| Fixed size that respects user font preferences (icon, border-radius, small UI detail) | `rem(px)` |
| Sub-pixel precision (e.g. `1px` border) | raw `px` |
| Component that only spans a subset of the viewport range | `fluid((mobile-large: 16, tablet: 24))` with explicit stops |

## Naming conventions

- **Block names**: kebab-case with a numeric suffix — `text-1`, `content-image-2`, `accordion-1`
- **ACF field group titles**: `"Block: {block-name}"`, `"Custom Field: {name}"`, `"Global Field: {name}"` — the prefix controls where the JSON is saved
- **CSS classes**: blocks get `block block-{name}`; components get `component component-{name}`; both receive `data-block` / `data-component` attributes of the same name
- **WordPress block name**: always `acf/{block-name}` (e.g. `acf/text-1`) — set automatically by `scan_and_register_blocks()`
- **JS/CSS handles**: `{block-name}-style` and `{block-name}-script` — registered automatically if the compiled files exist in `public/blocks/`
- **PHP functions**: `snake_case`; helpers prefixed with `core_` when registered as WP filter/action callbacks in `core/`

## Native modules built on top of the framework

Features added directly as self-contained files/folders under `modules/` instead of third-party plugins — not blindly auto-required like `core/`/`app/` (`functions.php` requires each module explicitly, since a recursive require would double-load MediaTrim's own internal `inc/` includes). Each is gated by a hardcoded `app/config.php` constant (hard kill switch, decided at code-load time — same "client can never toggle it" rationale as `SHOW_ACF_ADMIN`/`LOAD_LIBRARY_BLOCKS`) **and** a same-purpose ACF field on the **Feature Toggles** options page (day-to-day runtime toggle a client-facing admin can flip without touching code). Both must be `true` for the feature to actually be active — `get_field(...) !== false` is the check (not a plain bool cast), since ACF returns `null`, not the field's `default_value`, until the page has been saved once.

| Feature | File(s) | Config constant | ACF field (Feature Toggles page) |
|---|---|---|---|
| ACF admin UI | `core/acf.php` | `SHOW_ACF_ADMIN` | `feature_show_acf_admin` |
| `library/` blocks | `core/blocks.php` | `LOAD_LIBRARY_BLOCKS` | `feature_library_blocks` |
| MediaTrim (media optimization) | `modules/media-optimizer/` (own module, see below) | `MEDIA_OPTIMIZER_ENABLED` | `feature_media_optimizer` |
| SVG upload support | `modules/svg-support.php` | `ALLOW_SVG_UPLOAD` | `feature_svg_upload` |
| Portfolio password gate | `modules/portfolio-gate/` | `PORTFOLIO_GATE_ENABLED` | `access_enabled` (Site Settings → Portfolio Access) — single shared password (plain ACF text field `access_password`, visible to admins by client request), signed `STYXKEY_vp_access` cookie (Pantheon varies its edge cache on `STYXKEY*`), lifetime in days, password checked over AJAX (no reload on a wrong password; admin-post.php fallback without JS), "confidential" loading screen with a ring that fills over the hold time, REST + listing AJAX gated, per-IP rate limit. Logged-in editors bypass it. Uploaded media URLs are **not** covered. |
| Duplicate Post | `modules/duplicate-post.php` | `ALLOW_DUPLICATE_POST` | `feature_duplicate_post` (+ `duplicate_post_types` checkbox, choices populated dynamically from `get_post_types(['public' => true])`) |

**SVG upload support** (`modules/svg-support.php`) — upload restricted to `manage_options`. Every uploaded file is sanitized via `DOMDocument` (strips `<script>`, `on*` event-handler attributes, `javascript:` URIs, `<foreignObject>`) and **fails closed**: a file that fails to parse as XML, or contains a `<!DOCTYPE>`, is deleted and the upload rejected outright (via WP's `wp_handle_upload` `'error'` key convention) rather than ever falling back to unsanitized content — the earlier fallback-on-parse-failure behavior was a real sanitizer-bypass vector (a file crafted to be "invalid enough" for `DOMDocument` to reject, while still lenient enough for a browser's own SVG parser to execute). Builds attachment metadata by hand (`core_svg_attachment_metadata()`) since WP's raster image editors can't read SVG, and disables `srcset` generation for SVG attachments entirely (`core_svg_disable_srcset()`) — a vector has one file for every size, and WP core's `wp_calculate_image_srcset()` derives each candidate URL from the metadata's `file` key, silently dropping the uploads year/month subfolder if that value isn't a proper relative path. This is exactly what happened to pre-existing SVGs uploaded through a different SVG plugin once that plugin (which likely suppressed srcset for SVG itself) was deactivated — confirmed root cause of a real broken-logo report; fixed by disabling srcset unconditionally and repairing the legacy attachments' stored `file` value to include the date folder.

**Duplicate Post** (`modules/duplicate-post.php`) — nonce-protected "Duplicate" row action, plus a matching bulk action (`bulk_actions-edit-{post_type}` / `handle_bulk_actions-edit-{post_type}`, registered per allowed post type on `current_screen`) for cloning many posts at once — handy for seeding mock content (pagination/category testing, etc.). Both paths are gated by **both** `current_user_can($post_type_object->cap->create_posts)` (type-level — can this user create posts of this type at all) **and** `current_user_can('edit_post', $post->ID)` (instance-level — can this user touch *this specific* post), checked **per post ID** in the bulk handler's loop, not once for the whole request. The instance-level check is required, not optional: type-level alone would let a user duplicate someone else's private/draft content of a post type they can otherwise create (a real IDOR). This is not a hypothetical — WordPress core already verifies the bulk-action nonce before the handler runs, but that nonce only proves the request came from this list-table screen, not that the user may touch every post ID submitted alongside it; Yoast Duplicate Post's own bulk handler was missing exactly this per-post check as recently as CVE-2026-1217 (Contributor+ could bulk-duplicate/overwrite posts they didn't own). Clones post data, every postmeta entry (ACF fields and the featured image are just postmeta — no special-casing), and taxonomy terms. `wp_insert_post()` calls must be wrapped in `wp_slash()` — passing already-unslashed content through unwrapped corrupts any literal backslash in it (e.g. the `\uXXXX` escapes ACF blocks store in `post_content`'s JSON comments), since `wp_insert_post()` calls `wp_unslash()` internally expecting `$_POST`-shaped input. The single-row action redirects back to the referring list-table page (not the new draft's edit screen), with a dismissible admin notice linking to the copy; the bulk action shows a count notice instead.

**Feature Toggles options page** (registered in `app/options-pages.php`, right after "Scripts") — gated to specific user ID(s) via a dedicated `view_feature_toggles` capability (not a role), granted only to the ID(s) in `FEATURE_TOGGLES_USER_ID` (`app/config.php` — accepts a single int or an array) through a `user_has_cap` filter. A capability check (unlike just hiding the menu item) also blocks direct URL access. `core_acf_show_admin()` always returns `true` for that user regardless of what `feature_show_acf_admin` is set to, so they can never lock themselves out of turning ACF's admin UI back on. `is_feature_toggles_admin(?int $user_id = null)` (`app/options-pages.php`) is the reusable check for this — use it, don't reimplement the ID/array comparison elsewhere.

**Any new admin JS that renders WP-sourced text (titles, etc.) via `innerHTML` must escape it first** (`div.textContent = text; div.innerHTML` is the pattern used throughout `modules/media-optimizer/assets/*.js`) — a post/attachment title is attacker-influenceable by any role that can set one, and relying on "WP already sanitizes it" is not a safe assumption to build a new admin screen on.

## MediaTrim module (`modules/media-optimizer/`)

Self-contained media-optimization module — WebP generation, opt-in destructive recompression, and thumbnail regeneration, each with its own admin page under a "MediaTrim" top-level menu, chunked AJAX bulk tools (queue endpoint + small-batch processing endpoint, so a big library can't time out one request), an admin-bar "Process now" shortcut, and on-upload auto-processing via a `shutdown`-hook + `fastcgi_finish_request()` — not WP-Cron alone, since `DISABLE_WP_CRON` is Pantheon's own standard config and pseudo-cron never fires under it regardless of page views (WP-Cron is still scheduled too, as a harmless safety net for hosts with a real system cron pointed at `wp-cron.php`).

Deliberately uses **only WordPress core functions** — no theme `component()`/`render()` calls — and its own namespace (`MediaOptimizer\`), built this way from the start so it can be lifted into a standalone plugin later with minimal changes. Its `Settings` class (a single `media_optimizer_settings` option, not ACF) is fully self-contained; the *only* theme-specific integration point is the `feature_media_optimizer` ACF field check in its bootstrap's deferred `init` callback (see the Feature Toggles table above) — that line, and that line only, is theme-coupled. (That deferral itself matters: the module's `::init()` calls used to run immediately at file-require time; they're now deferred to the `init` action specifically so `get_field()` — unreliable that early in the request — can be checked safely.)

**To extract as a standalone plugin:**
1. Move `modules/media-optimizer/` to `wp-content/plugins/media-trim/` (or chosen slug); add a real plugin header comment block to the bootstrap file.
2. Replace `MEDIA_OPTIMIZER_URL`'s `get_template_directory_uri() . '/modules/media-optimizer'` with `plugins_url('', __FILE__)` (or `plugin_dir_url(__FILE__)`) — `MEDIA_OPTIMIZER_DIR`'s `__DIR__` is already plugin-safe, no change needed.
3. Drop the top-of-file `MEDIA_OPTIMIZER_ENABLED` constant check — plugin activation/deactivation *is* that switch now.
4. Drop the `get_field('feature_media_optimizer', 'option')` check in the deferred `init` callback — that's the one ACF/theme dependency being removed; `Settings::optimize_on_upload()` etc. remain the module's real, self-contained on/off controls.
5. Add `register_activation_hook()` / `register_deactivation_hook()` (clear the scheduled `Upload_Hook::CRON_HOOK` event on deactivate).
6. Swap every `'rear-theme'` text-domain string in `modules/media-optimizer/**` to a new plugin-specific domain; set up its own `load_plugin_textdomain()` + `.pot`/`.po`/`.mo` (same shape as `.claude/skills/wp-i18n-sync/SKILL.md`, different domain and scan path).
7. Remove the `require_once .../modules/media-optimizer/media-optimizer.php` line from `functions.php`, and remove the `feature_media_optimizer` field from the Feature Toggles ACF group — no longer applicable once plugin activation is the switch.
8. Test on a staging copy before swapping out the theme-embedded version in production — the migration touches file paths, URLs, and removes a real dependency layer, all at once.

**Non-negotiables** — full detail, rationale, and the incident history behind each rule live in the skill docs; these lines exist only so no session misses them:

- **Opacity-derived colors are always `color.adjust($color, $alpha: X)`, never a hardcoded `rgba()` literal.** Palette-independent tokens use a literal hex as the first argument — still wrapped in `color.adjust()`. (`figma-to-scss.md` §3)
- **A static (Mobile == Desktop) dimension reconstructed from Figma is `rem(value)`, never a bare number — `0` is the only exception.** Hard rule, no per-token judgment. (`figma-to-scss.md` §4)
- **Figma→SCSS conflicts: trust Figma's `value` and apply — only stop to ask if it would break the code** (unresolvable alias chain, invalid output, orphan variable with no SCSS counterpart). (`figma-to-scss.md` §7)
- **A resolved color alias must be written as the literal SCSS variable it terminates at — never swapped for a different variable that merely holds an equal value today**, even one matching a sibling rule's existing idiom in the same file. Two variables being numerically equal is not license to substitute one for the other. (`figma-to-scss.md` §2, `figma-to-component-scss.md` §6 gotcha 8)
- **`font-size`, `font-family`, and `font-weight` are live-bound on every text style** via `setBoundVariable` (plus colors and Dimensions bars) — editing one of these Typography variables updates every style/instance using it in real time. `font-family` is a plain STRING variable; `font-weight` is a bare number (e.g. `700`) — neither has a unit-mismatch problem.
- **`line-height` and `letter-spacing` are deliberately left UNBOUND on every text style**, as plain percent literals (e.g. `120%`) matching `{key}/line-height-ratio` / `{key}/letter-spacing-ratio` in the `Typography Static` collection. This is intentional, not a gap: the theme's SCSS (`_variables.scss`) stores these as a bare unitless ratio (`line-height: 1.2`) or `em` value (`letter-spacing: 0.1em`) applied on top of an already-`fluid()` font-size — mode-independent by design, because the ratio scales automatically with whatever font-size is active. Figma's `setBoundVariable('lineHeight'|'letterSpacing', …)` **always** interprets the bound FLOAT as raw pixels, never percent — there is no way to bind a percent-semantics variable to these fields, and Figma has no live cross-variable formula (its `Expression`/`MULTIPLICATION` type exists only for prototyping/interaction conditions, not for computing one variable's value from another). Binding them per-breakpoint pixel values was tried and reverted (2026-07-21) — it made the Figma canvas render "correctly" at two fixed widths but produced numbers with no code equivalent, since the SCSS ratio is exactly what needs to round-trip via figma-to-scss/scss-to-figma, not a derived px snapshot. **When a `-ratio` value changes**: update the literal percent on the text style by hand (or ask for it) to match, and update the SCSS number in the same pass — there's no automatic link in either direction.
- **Component-level syncs audit every visual property on every variant, one component at a time** — never just the properties that were mentioned as changed. (`figma-to-component-scss.md` §§1–2)
- **After manually repositioning a `COMPONENT_SET`'s variants apart, both resize AND relocate the set's own bounding box** — resizing alone leaves a stale-origin dead zone that's still clickable in the live Figma file and intercepts clicks meant for other content. A working `createInstance()` test does not prove the bounding box is correct. (`component-to-figma.md` §4.3)
- **Component-scoped variables live in `Components` (dimensions) / `Components Colors` (colors), never directly in the global `Dimensions`/`Colors` collections** — and color variables use role-based names (`color-hover`, `border-active`), not renamed globals. (`component-to-figma.md` §2)
- **A Sections Library archetype frame's outer `paddingTop`/`paddingBottom` binds to `Vertical Spacing/vertical-default|none|small|medium|large`, never `Spacing/gap-*` (e.g. `gap-jumbo`) or a raw unbound number** — mirrors the code rule that a block's SCSS starts with `padding: $vertical-default 0;`. Exception: full-bleed/manually-positioned archetypes (`layoutMode: NONE` with an absolute-positioned overlay) don't use padding at all. (`scss-to-figma.md` §9)
- **A Sections Library archetype frame's horizontal inset is TWO nested layers, not one** — the outer canvas (1440 desktop / 360 mobile) gets zero horizontal padding of its own; a dedicated `Wrapper` child frame carries the fixed `Wrapper/*` width (1360 default) and its own `paddingLeft`/`paddingRight` bound to `Wrapper/horizontal-padding`, mirroring `.wrapper`'s real `max-width` + `padding` + `margin: 0 auto` in `_wrapper.scss`. Padding baked directly onto the outer canvas alone renders content ~80px too wide and was wrong across nearly every archetype in the library until caught. (`scss-to-figma.md` §10)
- **Editing a color variable's value resets every paint bound to it to opacity 1, file-wide** — this is why "transparent" states kept going solid after palette edits. A component's transparent state is therefore always an empty paint array (`fills = []` / `strokes = []`), never an opacity-0 paint bound to a variable. All built components use the empty-array pattern as of 2026-07-05; if a transparent state renders solid, something reintroduced a bound paint — convert it, don't re-fix its opacity. (`component-to-figma.md` §4.15, `scss-to-figma.md` §7.11)
- **Every text node gets its matching local Text Style applied (`node.textStyleId = style.id`), not just a bound `fontSize` variable.** Binding the variable alone is visually identical but leaves the node unlinked from the design system's actual reusable style object — missed across every Sections Library page built before 2026-07-07 because the frame recipe never said to do it. Map by `style.boundVariables.fontSize` matching the node's own bound variable (mechanical 1:1 lookup), applied right after building each section, not as an end-of-build cleanup pass. (`scss-to-figma.md` §12)
- **`figma.createAutoLayout()` defaults to a visible white fill — every script that creates more than one auto-layout frame must run the stray-fill audit (find+clear any auto-layout `FRAME` with an unbound `SOLID` fill) before returning, not just remember `fills = []` on each node.** Recurred across Accordion, Carousel, Location, and Header despite being documented since early sessions — a prose reminder doesn't survive a script writing 10+ `createAutoLayout()` calls in a row, especially on secondary/nested containers. Treat the audit as a mandatory mechanical step, not a thing to keep in mind while writing the script. (`component-to-figma.md` §4.2)
