# Component code → Figma — build a new component from PHP/SCSS

Companion to the other three `figma-sync` docs, but a different direction/layer than any of them:

| Doc | Layer | Direction |
|---|---|---|
| `scss-to-figma.md` | `_variables.scss` tokens | code → Figma |
| `figma-to-scss.md` | `_variables.scss` tokens | Figma → code |
| `figma-to-component-scss.md` | one component | Figma → code (sync a designer's edits back) |
| **this doc** | one component | **code → Figma (build it there for the first time)** |

Use this doc when the component doesn't exist in Figma yet and the source of truth is the PHP/SCSS pair in `src/content/components/{tier}/{name}/`. Once built, `figma-to-component-scss.md` takes over for any future "designer edited Figma, sync back to code" requests.

Built from eight real components (Button, Buttons, Icon, Pagination, Social Media, Swiper Control, Play Button, Image Video) across several sessions on this theme's Figma file. Every rule below was hit as a real bug, not written speculatively. Also load `figma-generate-library` and `figma-use` before any `use_figma` call — those cover the generic Plugin API mechanics and workflow phases; this doc covers what's specific to *this project's* conventions and the bugs that don't show up in generic guidance.

**Not every component built this way is meant to sync back to code.** Image Video (built alongside Play Button) is Figma-only — a design tool for assembling mockups, deliberately never round-tripped through `figma-to-component-scss.md`. Confirm with the user up front whether a component is spec-for-future-code (like Play Button, built *ahead of* a real SCSS change that didn't exist yet) or purely a Figma-side authoring aid — it changes whether dimension variables/breakpoint variants are even worth building (a freeform, designer-resizable content area doesn't need `Components`-collection sizing tokens the way fixed chrome does).

## 1. Two component shapes — pick before building anything

**Single-tier** (Button, Icon): the component's variant model *is* the whole story. One `COMPONENT_SET`, every variant is directly what a designer would drag into a page. Use this when the code's `component()` call renders one self-contained visual unit per call.

**Two-tier** (Pagination): the code's `component()` call wraps something composite or dynamic (e.g. `pagination.php` wraps WordPress's `paginate_links()` — a whole nav bar assembled from many individually-styled sub-elements, not one fixed visual). Build:
1. An atomic **item** `COMPONENT_SET` (e.g. `Pagination Item`) — one master per real visual state combination. This is documentation/reference, not draggable into a page.
2. A second, small `COMPONENT_SET` (e.g. `Pagination` itself, 1 property = the component's own top-level variant like Style) assembled from **instances** of the item set — this is the actual reusable, block-ready component. Composed via `createInstance()` + auto-layout, not new geometry.

**How to tell which shape a component needs**: does the PHP file make repeated/dynamic sub-renders inside one `component()` call (a loop, a WP function generating variable-length markup, multiple distinct sub-elements with independent state) with no `component()` calls for the sub-parts? → two-tier. Does it render one fixed visual shape per call? → single-tier.

**This rule is about code structure, not really about whether an item COMPONENT_SET is warranted — check the actual visual chrome too.** Swiper Control's `swiper-controls.php` calls `component('icon', [...])` per sub-part (prev/next), which by the letter of the rule says single-tier (reuse Icon's existing masters directly, like Buttons reuses Button). But its hover colors (`$primary`/`$light-1`) don't match any existing Icon variant (`$accent`) — Icon has no variant that produces the needed look. Built a dedicated item COMPONENT_SET anyway, confirmed with the user first since it was a genuine judgment call. **When a single-tier candidate's required visual state doesn't already exist on the component it would reuse, that's a strong signal to give it its own item set instead of leaning on undocumented per-instance overrides** — even though the code technically just calls the existing component.

**Sub-elements that only differ by content, not styling, are never separate master variants.** Pagination's `Prev`/`Next` arrows share Number's exact box/color/size rules (confirmed against the SCSS: no `.prev`/`.next`-specific styling exists) — they're `Number`'s Default-state master instantiated with `.characters` overridden to `<`/`>`, never their own `Type` variant. This keeps the variant matrix from multiplying for zero visual reason, and means a future style change to the shared box only has to happen once. Before modeling any code-level distinction (a different CSS class, a different HTML tag) as a Figma variant axis, check whether the actual computed styles differ — a different selector with identical declared properties is not a different variant.

## 2. Component-scoped variables — two collections, not one

Two dedicated collections hold every component-scoped variable in this file (added 2026-07-02, migrated Button/Icon/Pagination's originally-scattered variables into this structure):

- **`Components`** (Mobile/Desktop modes) — dimension variables only: sizes, gaps, border widths, radii, opacity. `{ComponentName}/{property}`, e.g. `Button/height`, `Pagination/radius`.
- **`Components Colors`** (single "Default" mode) — color variables only, split into its own collection specifically because colors don't vary by breakpoint; giving them Mobile/Desktop modes is pointless duplication of the same alias in both slots. `{ComponentName}/{Style}/{role}`, e.g. `Pagination/Dark/color-hover`.

**Why component-scoped at all, instead of binding straight to the global `Dimensions`/`Colors` tokens**: the point is letting a designer tune one component's height/padding/radius/color independently over time without touching (or being blocked by) the shared token scale. A component's value differing from the nearest-looking global token is the intended behavior, not a discrepancy — don't "fix" a component variable to match a global one just because they're close.

**Color variables use role-based names, not flat value-mirroring names.** `Pagination/Dark/color-hover` (role), never `Pagination/dark-blue` or a bare rename of the global token like `Pagination/primary` (value-mirror — this was actually tried first and explicitly rejected: "use better variable names... something like color-default, background-default, border-default, color-active, color-hover"). A flat value-mirroring name just re-labels a code token; a role name tells a designer what property it actually drives. Standard role vocabulary that's worked so far: `color-default`, `color-hover`, `color-active`, `border-default`, `border-hover`, `border-active`, `background-default`, `background-hover`, `background-active` — adapt to whatever states the component actually has (don't invent `-active` if the component has no current/selected concept).

**Create a role variable for every state even if several currently resolve to the same value.** `color-hover` and `color-active` were kept as two separate variables even though the SCSS makes them visually identical today — the point is that a future SCSS change differentiating them becomes a one-line alias repoint instead of a structural rebuild. The only state genuinely worth *omitting* a variable for is one with literally no CSS declaration for that property (e.g. don't invent `border-hover` if hover never touches border color in code) — check the actual selectors, don't assume symmetry.

**A default state with no visible value (e.g. `background: transparent`) still gets a real variable, aliased like its siblings, with `opacity: 0` on the paint** — not an empty `fills: []`. This keeps the binding future-proof (someone can raise the opacity later without creating a variable from scratch) while staying visually invisible today. See §4 for the exact API sequencing this requires — getting it backwards silently produces `opacity: 1` instead.

**Migrating an existing variable to a new collection**: Figma has no "move" operation. Create the new variable, recursively rebind every node reference (see §4's `strokeWeight` split gotcha — the single most commonly missed property), update any `setExplicitVariableModeForCollection` calls to the new collection's mode IDs, verify visually, **then** delete the old one. Deleting before rebinding everything leaves dangling references that render fine on cached values until the file is reloaded — caught only by re-inspecting `boundVariables` directly, never by a screenshot.

**One flat `{ComponentName}/` prefix per component — never split into `{ComponentName} Item/` for the item tier and `{ComponentName}/` for the assembled tier.** Tried on both Buttons and Social Media, in both cases the user rejected it after the fact ("I don't see a point to separate the variables... if it's the same component") and it had to be migrated back to one prefix. A two-tier component (§1) still gets exactly one variable namespace shared by both its item masters and its assembled masters — the tier distinction lives in the node/COMPONENT_SET structure, not in the variable name.

**Width and height (or any two dimensions that happen to match today) always get two separate variables, never one shared variable bound to both properties** — even when every current value is identical. Hit on Icon's and Social Media's `wrapper-size` (one variable bound to both `width` and `height`) after the user pushed back: a shared variable blocks a designer from ever making width ≠ height later (e.g. a pill instead of a circle) without a migration. Split into `wrapper-width`/`wrapper-height` (or `icon-width`/`icon-height`, etc.) from the start, even for a component whose box is currently meant to be square.

**`OPACITY`-scoped variables (e.g. `disabled-opacity`) use a 0–100 range, not a 0–1 fraction.** Binding a variable created with the value `0.5` to `node.opacity` resolves to `0.5%` opacity (visually invisible), not 50% — Figma interprets the stored number as a percentage for this scope. Hit once on Button (documented, not generalized here) and hit again fresh on Swiper Control's `disabled-opacity` in a later session, because the rule lived only in Button's own memory file, not here. **Always use `50`, not `0.5`, for a "50% opacity" `OPACITY`-scope variable — check this specifically every time one is created, the 0–1 guess is the natural first instinct and wrong.**

## 3. INSTANCE_SWAP for interchangeable content (icons, not text)

When a component slot needs to show one of several interchangeable *shapes* (Icon's 6 glyphs), expose a single `INSTANCE_SWAP` component property rather than a variant axis per option — a variant per icon multiplies the matrix for no reason (`cs.addComponentProperty('Icon', 'INSTANCE_SWAP', defaultComponentId)`).

**Restrict the swap picker with `preferredValues`** — `cs.editComponentProperty(propKey, { preferredValues: [{type:'COMPONENT', key: glyphId}, ...] })` — or the dropdown lists every component in the entire file, not just the intended options. Must be updated every time a new option is added to the set, or it won't appear in the picker.

**Every swappable master needs a roughly square (or otherwise uniform) bounding box**, even if the artwork inside isn't. The swap slot is a fixed-size container; a master whose own geometry bounding box is far from that aspect ratio (a thin divider line, a wide arrow) gets **stretched** to fill it when swapped in. Fix: resize the master's own outer frame to the uniform canvas size, center the artwork inside, and set the artwork's `constraints = {horizontal:'CENTER', vertical:'CENTER'}` — Figma's default `SCALE`/`SCALE` constraint will re-stretch the artwork the next time the frame is resized for any reason, so this isn't optional cleanup.

For interchangeable *text content* (Pagination's page numbers), don't use INSTANCE_SWAP at all — just `createInstance()` + override `.characters` directly. INSTANCE_SWAP is for swapping which *component* renders, not for varying a string.

**A per-instance fill/color override does not survive an `INSTANCE_SWAP` property change on that same instance.** The override lives on the vector node *inside* the swapped-out glyph subtree; swapping to a different glyph master replaces that subtree entirely, silently reverting to the new glyph's own (often literal, unbound) default fill. Hit on Social Media's showcase strip and assembled row: built an instance, overrode its glyph's color correctly, then called `setProperties()` to swap the glyph — color reverted to black. **Any script that swaps an `Icon`/`Direction`/similar property on an existing instance must re-apply the correct color-role fill immediately after the swap, every time** — never assume a prior override survives.

**For a glyph that needs a mirrored counterpart (e.g. a left/right-pointing arrow), build a second real vector master with the path coordinates reflected, not a `relativeTransform` flip on an instance.** After expanding any `H`/`V` shorthand (§4.7) to get an absolute M/L/C/Z path, mirror every X coordinate (`newX = viewBoxWidth - x`) to produce a second, independent, correctly-wound path — used for Swiper Control's Prev arrow from the Next arrow's path. This avoids `relativeTransform` matrix edge cases entirely and produces a master that behaves identically to any other glyph master (screenshots fine, swaps fine, no special-cased node).

## 4. Known Plugin API gotchas (all hit and fixed across Button/Icon/Pagination)

1. **`figma.createVector()` defaults to a visible 1px black stroke.** Invisible at large sizes, but at icon scale it dominates thin strokes and makes any non-black fill look wrong regardless of what the fill is actually bound to. Always `vector.strokes = []` immediately after creating a vector — treat it as mandatory, not conditional on whether a stroke was intended.

2. **`figma.createAutoLayout()` defaults to a visible white fill.** Any auto-layout frame not meant to have a background needs `frame.fills = []` explicitly, or it renders as a stray white block, most noticeably on a dark backing.

    **This gotcha has recurred across many builds (Accordion, Carousel, Location, Wrapper double-inset, Header) despite being documented since early sessions — because it was only ever a prose reminder, and a script writing 10+ `createAutoLayout()` calls in a row reliably forgets it on the *secondary/nested* containers (nav items, accordion rows, action-link rows) even when it's correctly applied to the primary ones (outer canvas, Wrapper).** Remembering harder doesn't fix a recall failure at this volume — treat it as a mechanical, non-optional last step instead of a thing to keep in mind while writing the script:

    **Run this audit at the end of every `use_figma` call that creates more than one auto-layout frame, before returning** — it's cheap and catches exactly this class of bug regardless of how many nodes were created or how confident you are that you remembered `fills = []` everywhere:
    ```js
    // Every intentional fill in this design system is bound to a Colors variable
    // (never a hardcoded/unbound paint — see "never hardcode role→token"). So any
    // auto-layout FRAME carrying an unbound SOLID fill is, by definition, either
    // this default-fill bug or a token-binding violation. Either way, clear it.
    const strayFills = root.findAll(n =>
      n.type === 'FRAME' &&
      n.layoutMode !== 'NONE' &&
      Array.isArray(n.fills) &&
      n.fills.some(f => f.type === 'SOLID' && !f.boundVariables?.color)
    );
    strayFills.forEach(n => { n.fills = []; });
    // Include strayFills.map(n => ({id: n.id, name: n.name})) in the return value
    // so a stray-fill fix is visible in the script's own output, not just inferred
    // from a later screenshot.
    ```
    `root` is whatever frame(s) the script just built (or `figma.currentPage` for a full-page sweep). This is now a required step, not an optional cleanup pass — see the equivalent non-negotiable in the theme's `CLAUDE.md`.

3. **A `COMPONENT_SET`'s own bounding box must be both resized AND relocated after manually spreading its variants apart** (e.g. positioning two variants far from each other for a side-by-side display) — `.resize()` alone, without moving the origin, leaves the box anchored at its stale original `(0,0)` while content sits elsewhere, creating a large invisible dead zone that's still part of the set's clickable bounding rectangle in the live Figma canvas. This isn't cosmetic: a user clicking anywhere in that dead zone — which visually shows *other, unrelated* content sitting on top — selects the oversized set instead of whatever they meant to click. A temporary `createInstance()` test rendering correctly does **not** prove the bounding box is right; it validates the variant's own content, not the set's frame. The real fix: move the set's `x`/`y` to the children's actual min bounds, subtract that same offset from every child's local `x`/`y`, **then** `.resize()` to `(maxX-minX, maxY-minY)`. Verify by confirming no child has negative-offset space above/left of the set afterward — that's the correctness check, not a screenshot.

4. **`strokeWeight` is often actually four separate properties** (`strokeTopWeight`/`strokeBottomWeight`/`strokeLeftWeight`/`strokeRightWeight`), not the single `strokeWeight` field, whenever a uniform border was originally applied via `setBoundVariable('strokeWeight', ...)` — Figma silently expands it. Checking only `boundVariables.strokeWeight` during an audit or migration will report "nothing bound here" for a border that's very much bound, just split across the four directional fields. Always check (and rebind) all five names.

5. **Setting `opacity` on a paint object *after* calling `setBoundVariableForPaint` doesn't stick.** `{ ...setBoundVariableForPaint(paint, 'color', v), opacity: 0 }` silently reverts to `opacity: 1` on assignment to `.fills`/`.strokes`. Fix: put `opacity` on the *input* paint object passed **into** `setBoundVariableForPaint`, not spread onto its return value afterward.

6. **Instances don't reliably re-inherit every kind of master change** — this is the one place "rebind the master, everything downstream follows automatically" (which is otherwise a completely reliable pattern for plain `boundVariables` swaps, proven repeatedly) breaks down. After fixing a master's fill *opacity*, existing instances (built before the fix) kept rendering their own stale resolved value until fixed directly, node by node. Don't assume cascade for anything touching `opacity` or the shape of the fills/strokes array — verify each downstream instance explicitly rather than trusting the pattern that works for color/size rebinds.

7. **Figma's vector path parser rejects SVG `H`/`V` shorthand commands.** Before calling `createVector()` with a `d` attribute lifted from a real SVG file, expand any `H`/`V` to explicit `L` with the resolved coordinate — `H14V14` → `L14 0 L14 14` (carrying forward the correct running x/y). The parser throws on H/V outright, not a silent misrender.

8. **A script's own read-back of a value it just wrote is not proof the mutation succeeded correctly, and neither is `get_screenshot`/inline `node.screenshot()` on a `COMPONENT_SET`'s master variant specifically** — both can render blank/degenerate (a 1×1px image, or nothing) even when direct Plugin API reads (`get_metadata`, `boundVariables`, `visible`, `fills`) confirm the node is structurally correct. This was misdiagnosed once as a document bug and once correctly identified as a genuine bounding-box bug (#3 above) — the two look identical from a blank screenshot alone. **Disambiguate by creating a temporary `createInstance()` of the suspect master, screenshotting *that*, then deleting it** — if the instance renders correctly, the master's own content is fine and the issue is bounding-box/origin (§3); if the instance is also wrong, it's a real content bug worth chasing further.

9. **A blank/degenerate screenshot (including a `1×1px` result) can also mean the node is sitting outside an ancestor frame's `clipsContent: true` bounds** — a third, distinct cause from #8, easy to conflate with it. Building any new component in a category frame that's only tall enough for its *existing* content (before your new section is added) will silently clip your scratch/WIP work from every screenshot, master or instance alike, even though `get_metadata` confirms correct geometry. **Before concluding "known renderer artifact" (#8), check whether the target node's absolute position falls inside its nearest `clipsContent: true` ancestor's current width/height** — extend that ancestor frame's size first (safe and reversible; it's just a container), then re-screenshot. Only chase the #8 explanation once clipping is ruled out.

10. **An opaque backing rectangle added to a frame *after* the real content (e.g. via `appendChild` at the end of a build script) renders on top of that content, not behind it** — Figma z-orders children by their position in the parent's child array, and a freshly-appended node goes to the front. A backing rectangle meant to sit behind a `COMPONENT_SET` or a set of captions must either be inserted *before* that content in the child array (`frame.insertChild(index, backing)` at an index earlier than the content) or the content must be brought back to front afterward (`frame.appendChild(content)`, which moves an *existing* child to the end without duplicating it). Verify the final child order directly (`frame.children.map(c => c.name)`) rather than assuming your insertion order matches the visual stacking you intended.

11. **An intentionally-invisible (`opacity: 0`) paint fill reliably fails to apply correctly in two specific situations, confirmed independently across three components (Pagination, Social Media, Swiper Control) — treat both as expected, not surprising** (and see #15, which supersedes the opacity-0-bound-paint approach entirely for new work):
    - **On any `INSTANCE`, even one created fresh, *after* its master's own fill was already verified correct.** Not just a stale-instance-after-a-later-master-edit problem (the original, narrower framing) — a brand-new `createInstance()` call made *after* the fix can still resolve to `opacity: 1` at creation time. Any instance that needs an opacity-0 (or otherwise non-default) paint must have that paint re-applied directly on the instance, every time, regardless of when it was created relative to the master fix.
    - **When set as part of a larger batch script that also mutates other properties on the same node** (`cornerRadius`, `strokeWeight`, explicit variable mode, etc. all in the same call) — even though the exact same paint-construction recipe (opacity on the *input* object passed into `setBoundVariableForPaint`, per #5) had just been verified correct on a single node built in isolation moments earlier. Root cause not fully isolated; the reliable mitigation is process, not a code fix: **after any batch build that includes an opacity-0 (or other non-1) paint fill, read back every affected node's actual `.fills[0].opacity` in a fresh script, and if any are wrong, re-apply `.fills` alone on just those nodes in their own isolated call** — don't trust that a technique proven correct in isolation survives being folded into a larger batch mutation.

12. **After any variable value edit that changes a component's dimensions (designer-driven, in the live Figma file, between sessions), every dependent bounding box, backing rectangle, and column/row layout computed from the *old* dimensions goes stale and must be recomputed from live geometry — not reused from whatever was hardcoded at original build time.** A wrapper going from a 42px circle to a 60×30px pill overflowed both the item-tier grid's column width and its backing panels' width (both originally sized for the smaller box), and the assembled tier's `COMPONENT_SET` bounding box and its own backing rectangles were left stale entirely (never resized after the edit). Always re-read `.width`/`.height` on the actual current nodes and recompute layout from those values before assuming a previous session's positioning script is still valid.

13. **`figma.combineAsVariants(masters, target)`'s `target` argument reparents using page-absolute coordinates, not the target's local space — `appendChild`-ing the result into a frame afterward does NOT adjust `x`/`y` to compensate.** If `target` is `figma.currentPage`, the new `COMPONENT_SET`'s `x`/`y` come out correct in *page* space; moving it into a category frame with `frame.appendChild(cs)` right after leaves those same numbers in place, but they're now interpreted as *frame-local* coordinates — silently throwing the set far outside the intended area (e.g. an intended local y=190 becoming an absolute y in the thousands, well past every sibling section on the page). Always explicitly re-set `.x`/`.y` to the intended frame-local values immediately after any `appendChild` that crosses from one coordinate space to another — never assume pre-reparent coordinates still mean the same thing. Building the masters as children of the destination frame *from the start* (rather than combining on the page and moving the result) sidesteps this entirely, if the workflow allows it.

14. **A bounding-box overlap check against a `COMPONENT_SET`'s own outer frame produces false positives — check each real child instance's absolute rect instead.** A `COMPONENT_SET`'s frame spans its full grid including inter-variant gaps, so a crude "does node A's box overlap node B's box" test flags text sitting in a gap as "covered" even when nothing is actually painted there. When verifying whether documentation labels visually collide with actual button/icon instances, compute each child's *absolute* position (`cs.x + child.x`, `cs.y + child.y`, actual `width`/`height`) and test against those — not the parent set's bounding box.

15. **ROOT CAUSE of every "opacity-0 fill regressed to opacity 1" incident, discovered 2026-07-05: editing a color variable's value resets the opacity of every paint bound to that variable back to 1, file-wide.** Confirmed with a controlled sequence on the Button masters: 20 transparent-state paints verified at opacity 0 by fresh readback → only the bound variables' values were rewritten (a re-alias via `setValueForMode`; no node was touched) → all 20 paints read AND rendered opacity 1. Any variable value write triggers it — an agent re-aliasing a role variable, a designer editing a palette color in the Variables panel, or a token push from `scss-to-figma.md`. Every prior "mysterious regression" catalogued in #11 and in the Swiper Control history (5+ incidents of transparent pills going solid between sessions) matches this mechanism: the palette had been edited in between.

    **The rule for all new component work: a transparent state is expressed as an empty paint array (`fills = []` / `strokes = []`), never as an opacity-0 paint bound to a variable.** Empty arrays are immune to variable edits — Button originally shipped this way and never regressed until it was temporarily converted to opacity-0 bound paints, which then broke on the first palette remap; it was converted back (masters + all ~143 instances) the same day. Keep the role variable (e.g. `background-default`) defined in `Components Colors` even when nothing binds it in the transparent state — it documents intent and gives designers a ready-made variable to bind if they later make the state visible. As of 2026-07-05 **every component is on the empty-array pattern** — Swiper Control (pills, Default/Disabled) and Pagination Item (Default/Dots) were converted last, masters + assembled tiers + ~100 instances file-wide. If a transparent state ever renders solid again, some paint was rebuilt on the old pattern — convert it to an empty array rather than re-fixing its opacity.

16. **Replicating a stacked/fanned card effect (Swiper `cardsEffect`-style: offset + scaled + rotated background cards) needs `relativeTransform` with a corner pivot, not `node.rotation`.** `node.rotation` always rotates around the node's own *center*, which — for cards offset sideways and scaled down behind an active card — visibly sags/bulges above the active card's top edge (a shape rotating about its middle swings its far corners both up and down). The real effect (and the live rendered DOM, `matrix3d`-driven) keeps one corner anchored and swings the rest of the card around *that*. Reproduce it with the raw 2D rotation matrix, pivoted at the card's own top-left corner:
    ```js
    const rad = deg * Math.PI / 180;
    const cos = Math.cos(rad), sin = Math.sin(rad);
    // tx/ty = the pivot point (e.g. active card's top-left + a measured x-offset)
    node.relativeTransform = [[cos, -sin, tx], [sin, cos, ty]];
    ```
    Get the offset/scale/rotation numbers themselves from the real rendered DOM (`getBoundingClientRect()` on each `.swiper-slide` at a given state), not from decoding the CSS `matrix3d()` string or guessing — a 3D-perspective transform's 2D screen-space footprint doesn't correspond 1:1 to reasoning about its rotate/translate/scale inputs, but the *measured* footprint reproduces visually even in a 2D tool like Figma (confirmed: Carousel 16 fan cards, after 6 failed rotation-direction/pivot/magnitude attempts using `.rotation` and eyeballed values).

## 5. Font availability can silently regress between sessions

Confirmed real, not a one-off: a font that rendered correctly for an earlier-built component (Button uses "Google Sans Flex" via the `Action/Action Medium` text style) can become unavailable to `figma.listAvailableFontsAsync()` in a later session — 0 matches out of 7700+ fonts, confirmed by direct repeated testing, not a transient glitch that resolves on retry. This is a gap between what the Plugin API can access in a given session and what the user's own Figma client renders — not something fixable from the agent side by trying harder.

**When building any new text-bearing component, check font availability before writing any text nodes** (`figma.loadFontAsync({family, style})` wrapped in try/catch, using the exact family/style from the relevant Text Style). If it fails, tell the user directly and ask how to proceed (fallback font now / they apply the real style manually later / wait) rather than silently substituting — don't assume a fallback used once should be reapplied automatically in a later session without asking again, since the underlying availability can change between sessions in either direction.

## 6. Workflow checklist

1. Read the component's PHP + SCSS in full before writing anything to Figma. Note every prop, every state, every visually-distinct combination — this is the variant model, don't guess it from the component's name.
2. Determine single-tier vs two-tier (§1).
3. Check whether the component's category/section in Figma already implies placement (a "coming soon" list naming the component is not ambiguous — don't ask where it goes). **Before picking "free space" next to an existing component's docs, check every one of that component's existing backing rectangles' actual x/width — not just the bottommost or most-recently-eyeballed section.** A prior component's main variant grid and its lower showcase/reference strip can have different horizontal spans; the grid's own backing is often wider. Placing new content based on the narrower strip's extent alone silently overlaps the wider one.
4. Present a short plan (variant count, axes, any genuine judgment calls) and get a lightweight confirmation before the first `use_figma` write — not a full multi-phase gate every time, this project has enough precedent now that a concise plan is usually sufficient.
5. Create component-scoped variables first (§2), in the correct collection.
6. Build one representative variant, screenshot-verify it, **then** build the rest of the matrix — don't build all variants blind and discover a structural mistake 30 variants in.
7. Position variants, resize the `COMPONENT_SET`'s bounding box correctly (§4.3), add documentation (captions, backing panels for light/dark, block labels).
8. For two-tier components, build the assembled/usable component from item instances (§1) as a separate, explicit step.
9.
